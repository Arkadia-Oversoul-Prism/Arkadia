## Runtime & Persistence

**Why SQLite instead of Redis / Postgres?**
Single-node deployment. Zero extra infrastructure. WAL mode gives crash-safe atomicity.
Fits current scaling horizon. Revisit: Phase 5 horizontal scaling audit.

**Why `data/runtime.db` separate from `knowledge/arkadia.db`?**
Runtime state (jobs, goals) must not couple to knowledge state. Different backup, retention, and migration schedules. One corrupted DB must not take down the other.

**Why replace the in-memory queue at all?**
In-flight jobs are silently lost on process crash. The JSON snapshot is best-effort, not durable. SQLite WAL is crash-safe with no external dependency. (ADR-014 Decision 1)

**Why keep JSON backup files after migration?**
Rollback path. A single `git revert` of the migration commit must restore JSON behavior. JSON files preserved read-only until two stable SQLite cycles confirmed. (ADR-014)

## Architecture

**Why is the kernel forbidden from importing api/?**
Layer inversion: the kernel is more stable than the API surface. Stable layers cannot depend on unstable ones. Importing api/ prevents kernel from being tested in isolation and creates circular import risk. (ADR-015)

**Why is the Plugin Registry (Workstream E) delayed?**
Workstream B (runtime durability) has higher architectural risk. An undurable runtime cannot support a plugin system safely. B → E order is mandatory. (ADR-014)

**Why is Observability (Workstream D) third, not first?**
Observability instruments an existing system. The system must first be structurally stable (B) and capability-bounded (E) before instrumentation adds value. (CONTINUATION_LEDGER.md)

**Why is Layer Violation remediation (Workstream A) fourth?**
A runs after E because the Plugin Registry removes the `ALLOWED_TYPES` frozenset, which is itself a layer-violation-adjacent coupling. Clean E before cleaning A. (CONTINUATION_LEDGER.md)

**Why are Providers leaf adapters?**
Provider implementations change constantly (API upgrades, new models). The kernel must be able to swap providers without structural changes. Providers must receive keys via injection, not import them. (ADR-015, ADR-014 Decision 4)

**Why is `api/main.py` decomposition deferred to Phase 2?**
It is 2506 lines, high-risk to touch, and decomposition requires canonical domain types that don't exist until Phase 2. Touching it in Phase 1 for anything other than middleware (D) and Firebase extraction (A) is forbidden. (ADR-014)

## Tooling

**Why architecture fitness tests instead of code review?**
A rule that lives only in a document depends on every reader remembering it. A rule encoded in a fitness test is enforced by CI. (ENGINEERING_PRINCIPLES.md, Principle 7)

**Why REGISTERED_ARCHITECTURAL_DEBT instead of ALLOWED_VIOLATIONS?**
"Allowed" implies permission. These entries are scheduled liabilities — understood, assigned, and due for removal. Language shapes engineering culture.

**Why separate `REGISTERED_CIRCULAR_DEBT` from `REGISTERED_ARCHITECTURAL_DEBT`?**
Circular imports require a different detection mechanism (DFS graph) and a different registry format (cycle tuples vs. importer/imported pairs). Keeping them separate makes each list easier to read and exit-criteria easier to verify.

## Sequencing

**Why Phase 1 before Phase 2?**
Cannot canonicalize a domain whose runtime is undurable. Jobs lost on crash means no reliable state to build domain types against. (ROADMAP.md)

**Why Phase 2 before Phase 3?**
Cannot build a Knowledge Layer without stable domain types. "Knowledge" means different things in three places until Phase 2 gives it one canonical definition. (ROADMAP.md)

**Why no Event Bus, Redis, Kafka, microservices in Phase 1?**
Infrastructure does not fix architecture. A well-bounded system with SQLite will outlast a poorly-bounded system with Kafka. Solve boundaries first. (ENGINEERING_PRINCIPLES.md, Principle 3; ADR-014 explicit exclusion)
