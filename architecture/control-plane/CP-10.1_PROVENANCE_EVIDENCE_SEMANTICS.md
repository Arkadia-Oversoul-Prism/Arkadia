# CP-10.1 — PROVENANCE EVIDENCE SEMANTICS

**Status:** schema-only / normative / technology-neutral / read-only

## Purpose
Define the evidence semantics required before an authority claim can be evaluated as provenance. CP-10.1 does not select a mechanism.

## Core question
Which evidence family could, in principle, produce evidence sufficient to distinguish an authenticated human authority event from an assertion claiming that it occurred?

## Mechanism families
| Family | Strength | Limitation |
|---|---|---|
| Cryptographic | integrity, scope, time, delegation structure | cannot alone prove biological human presence |
| Session-bound | subject/session binding | cannot alone prove deliberate authorization |
| Interaction-bound | deliberate interaction evidence | cannot alone establish legitimate authority |
| Witnessed | independent corroboration | witness cannot create sovereignty |
| Structural | artifact, patch, PassSpec and HEAD integrity | cannot prove human origin |
| Hybrid | can compose complementary evidence classes | composition must preserve distinctions |

## Four-layer invariant
`EVIDENCE → PROVENANCE → AUTHORIZATION → EXECUTION`

Forbidden shortcuts include evidence→authorization, evidence→execution, crypto→authority, Firebase→authority, UI click→authority, and hash→human provenance.

## Required semantic burdens
- subject binding
- event-level binding
- event origin
- deliberate origin where required
- exact scope
- time and temporal validity
- delegation lineage
- expiry/revocation
- contradiction handling
- explicit UNKNOWN
- fail-closed evaluation
- inspectability
- provenance/authorization separation
- authorization/execution separation

## Result
CP-10.1 established the mechanism-family evaluation vocabulary while deliberately leaving mechanism selection open. It became the basis for CP-10.2's acceptance criteria and the later CP-10.5–CP-10.9 candidate arena.
