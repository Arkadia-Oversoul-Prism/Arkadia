# CP-10.3 — PROVENANCE COLLISION RESOLUTION CRITERIA

**Status:** schema-only / normative / technology-neutral / no mechanism / no implementation

## Primary collision
**CP102-G07:** PassSpec can be treated as human authorization.

Repository grounding found the semantic dependency in which PassSpec is described as, or treated as, the human authorization for the execution envelope. This is a semantic collision, not merely a missing field.

## Constitutional question
Can Arkadia introduce evidence of human-origin authority without allowing PassSpec, PatchApproval, K15, K3, or the evidence layer to silently become sovereignty?

## Required separation
`AUTHENTICATED SUBJECT → SPECIFIC AUTHORITY EVENT → PROVENANCE → AUTHORIZATION`

PassSpec must not independently constitute human-origin authorization. PassSpec may govern scope and execution constraints only after the authority boundary is resolved.

## Resolution state machine
`UNRESOLVED → COLLISION RECOGNIZED → RESOLUTION PROPOSED → RESOLUTION EVALUATED → RESOLUTION ELIGIBLE → HUMAN ACCEPTANCE → IMPLEMENTATION GATE → IMPLEMENTED → VERIFIED → COLLISION RESOLVED`

Non-collapses: ELIGIBLE ≠ SELECTED; SELECTED ≠ IMPLEMENTED; IMPLEMENTED ≠ VERIFIED; VERIFIED ≠ AUTHORIZED; RESOLVED ≠ SOVEREIGNTY CREATED.

## Falsification
F01: removing origin evidence leaves PassSpec sufficient → unresolved.  
F02: provenance is added while PassSpec remains an independent authority source → unresolved.  
F03: current approval semantics are merely renamed as provenance → unresolved.  
F04: K3 still treats PassSpec as sufficient human authority → unresolved.  
F05: downstream execution is used to retroactively establish provenance → unresolved.
