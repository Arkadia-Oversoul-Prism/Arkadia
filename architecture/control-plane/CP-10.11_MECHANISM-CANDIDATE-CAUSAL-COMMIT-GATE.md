# CP-10.11 — MECHANISM CANDIDATE / CAUSAL COMMIT GATE

**Status:** ISOLATED CANDIDATE / MECHANISM-PRESCRIPTIVE / NO IMPLEMENTATION / NO ENFORCEMENT / NO AUTHORIZATION CHANGE

**Parent chain:** `CP-10 → CP-10.1 → CP-10.2 → CP-10.3 → CP-10.4 → CP-10.5 → CP-10.6 → CP-10.7 → CP-10.8 → CP-10.9 → CP-10.10 → CP-10.11`

## 1. Purpose

CP-10.11 enters the mechanism frontier opened by CP-10.10.

It does not claim to solve provenance. It proposes one concrete mechanism class that can be placed into the existing arena and tested against the already-established vocabulary.

The candidate is deliberately narrow:

> **Causal Commit Gate:** a target authority event is admitted only after a subject-bound, pre-committed challenge is independently generated, physically or otherwise deliberately actuated by the subject, cryptographically committed before the target event, and consumed exactly once by the target event.

The candidate therefore attempts to establish a stronger relation than association:

```text
SUBJECT ACTION
      ↓
PRE-COMMIT
      ↓
TARGET EVENT ADMISSION
```

But the candidate does **not** treat that protocol relation as automatic proof of human causal origination. The mechanism must still survive the arena's human-origin tests.

## 2. Candidate mechanism claim — M1

### M1.1 Mechanism class

The candidate mechanism is a **causal commit gate** composed of five observable stages:

```text
CHALLENGE GENERATION
        ↓
SUBJECT ACTUATION
        ↓
PRE-COMMITMENT
        ↓
EVENT ADMISSION
        ↓
SINGLE-USE CONSUMPTION
```

The target event is not merely labeled as having been caused by the subject. The system protocol makes admission of the target event conditional on a prior commit that is bound to:

- a defined subject identifier;
- a specific target event class;
- a fresh challenge or nonce;
- a bounded time context;
- a unique event instance;
- a single-use commitment;
- the exact authority scope being requested.

### M1.2 Candidate causal relation

The mechanism proposes the following protocol relation:

```text
C = Commit(S, challenge, event_class, scope, time)

E is admissible only if:

Valid(C, S, event_class, scope, time, E) = TRUE
```

The important property is not the encoding itself. It is the **precondition relationship**:

```text
WITHOUT VALID C
        ↓
TARGET E CANNOT BE ADMITTED
```

The candidate therefore supplies a mechanism-level causal dependency between the pre-commit and the target event.

It does not yet establish that the human subject caused the pre-commit.

## 3. Positive instantiation — M2

A successful implementation of this candidate would have to produce an independently inspectable event sequence containing, at minimum:

```text
C0 = fresh challenge generated before E
C1 = subject-bound actuation observed
C2 = commitment recorded before E
C3 = commitment bound to exact E-class and scope
C4 = E admitted only after C2/C3
C5 = commitment consumed exactly once
C6 = immutable ordering evidence for C0 < C2 < E < C5
```

The positive observable is therefore not:

```text
EVENT_CREATED_BY = S
```

It is the independently inspectable protocol fact that:

```text
E COULD NOT BE ADMITTED
WITHOUT THE PRECEDING SUBJECT-BOUND COMMITMENT C
```

That is the mechanism-level observable this candidate contributes.

## 4. What this mechanism establishes

If the implementation satisfies the specified conditions, the candidate may establish:

```text
COMMITMENT PRECEDENCE
COMMITMENT/EVENT DEPENDENCE
SINGLE-USE EVENT BINDING
SCOPE BINDING
TEMPORAL BINDING
```

It may therefore discriminate the following protocol worlds:

```text
WORLD A
valid pre-commit exists → event admitted

WORLD B
no valid pre-commit → event rejected

WORLD C
valid pre-commit for different event/scope → event rejected
```

This is stronger than retrospective attribution because the target event is protocolically dependent on the earlier commitment.

However:

```text
PROTOCOL CAUSATION
        ≠
HUMAN CAUSAL ORIGINATION
```

The candidate therefore enters the arena as a mechanism for testing the latter, not as proof that the latter has already been achieved.

## 5. False-positive distinctions — M3

The candidate must discriminate at least the following:

| Alternative relation | Required distinction |
|---|---|
| Authentication | Identity association is insufficient without the causal commit sequence. |
| Interaction | Mere interaction must not generate a valid commit unless the defined actuation occurs. |
| Attestation | A later assertion cannot substitute for the pre-commit. |
| Precedence | Timestamp order alone cannot satisfy the gate. |
| Event identity | Event IDs cannot create the causal relation after the fact. |
| Automation | An automated process must not be able to manufacture a valid human actuation under the tested threat model. |
| Replay | An old commitment must fail freshness/single-use validation. |
| Delegation | A delegated actor must not satisfy a subject-specific human-origin requirement unless explicitly authorized as a different subject class. |
| Inheritance | A derived event must not inherit origin merely because its parent event did. |
| Retrospective labeling | Adding origin metadata after E cannot satisfy the pre-commit requirement. |
| Witness/association | Presence of a witness or observer is not itself the causal mechanism. |

The automation distinction is explicitly unresolved until a threat model and actuation channel are selected and tested.

## 6. Deliberate-origin problem

CP-10.6 requires discrimination between deliberate origination and interaction, automation, replay, delegation, inheritance, derivation, and downstream execution.

The Causal Commit Gate addresses only part of that burden.

A valid commit demonstrates that a defined actuation occurred before E and that E depended upon it.

It does **not** by cryptographic construction alone prove that a human consciously intended the actuation.

Therefore the candidate records:

```text
DELIBERATE HUMAN ORIGIN: UNPROVEN
PROTOCOL CAUSAL DEPENDENCE: CANDIDATE OBSERVABLE
```

Any stronger claim would violate the CP-10.10 boundary.

## 7. Human-origin evidence requirement

To advance beyond candidate status, the arena must specify an actuation mechanism capable of being evaluated under a declared threat model.

Possible actuation classes include, but are not limited to:

- dedicated physical control;
- hardware-backed user presence;
- challenge-response requiring contemporaneous user action;
- supervised human ceremony;
- another mechanism capable of producing an observable that automation cannot reproduce within the declared threat model.

No one of these is selected by this document.

The candidate therefore deliberately separates:

```text
CAUSAL COMMIT MECHANISM
        ≠
ACTUATION MECHANISM
        ≠
HUMAN-ORIGIN PROOF
```

Selecting the actuation mechanism is a subsequent evaluation decision.

## 8. Counterfactual test

The candidate must survive a controlled counterfactual:

```text
A. Same subject identity, no valid pre-commit → E rejected.
B. Valid pre-commit, wrong event class → E rejected.
C. Valid pre-commit, wrong scope → E rejected.
D. Valid pre-commit, replayed → E rejected.
E. Valid pre-commit, correct binding → E admitted.
```

If E can occur in any protected path without the required C, the causal gate fails.

If E can occur only because a later assertion retroactively marks C as valid, the candidate fails the non-circularity test.

## 9. Threat-model tests

The candidate must explicitly test:

### T01 — Automation
Can an automated process create the same valid actuation without the required human action?

### T02 — Replay
Can a previously valid C be reused to admit a second E?

### T03 — Delegation
Can another subject produce C while E is attributed to S?

### T04 — Precomputation
Can an attacker prepare C before the actual human decision without invalidating the causal interpretation?

### T05 — Substitution
Can an attacker replace the target event after C is committed?

### T06 — Race
Can E be admitted through a concurrent path that bypasses C?

### T07 — Recovery
Can recovery, retry, queueing, or replication create E without preserving the same causal dependency?

### T08 — Retrospective labeling
Can metadata be added after E to make an invalid sequence appear valid?

### T09 — Derived event
Can E2 inherit the apparent origin of E1 without a new valid commit?

### T10 — Administrative override
Can an operator bypass the gate while retaining the same provenance claim?

Any unbounded positive answer is a candidate failure unless the exception is explicitly modeled and excluded from the protected authority path.
